FastOrder S.A.
Pedidos con Angular y PWA

Propuesta e implementación académica mobile-first para consultar un menú, conservar un carrito sin conexión y coordinar la entrega con un backend mediante pedidos idempotentes.

Resumen ejecutivo

FastOrder combina el app shell Angular con un menú de demostración, filtros por categoría, carrito persistente en IndexedDB y una cola local de pedidos. La experiencia distingue una orden guardada en el dispositivo de una orden aceptada por el restaurante. Cuando la conexión vuelve o el usuario abre de nuevo la aplicación, la cola intenta sincronizarse con el servidor.

Límite del prototipo: este repositorio contiene el frontend; no incorpora API, base de datos de pedidos ni emisor Web Push. El menú y sus precios son datos de muestra. La aceptación, inventario, idempotencia y estados reales requieren el backend documentado en README.md.

Arquitectura y comportamiento offline

App shell y menú

Angular Service Worker precarga la aplicación. El servicio del menú emite primero la copia IndexedDB y vuelve a consultar /data/catalogo.json; la respuesta nueva sustituye la copia local. Es SWR en la capa de servicio, combinado con freshness del NGSW.

Carrito y sincronización

El carrito y cada pedido se escriben en IndexedDB. El UUID permanece estable como Idempotency-Key. La app intenta enviar al iniciar o al recibir el evento online; los fallos dejan el pedido pendiente y visibles para el usuario.

Estado del pedido

La API es la autoridad. La app consulta el estado cada 15 segundos mientras está abierta y procesa push entrantes. El rastreador presenta Recibido, En preparación y Listo.

Instalación y manifest

El banner responde a beforeinstallprompt. El manifest define nombre, rutas, modo standalone, colores gastronómicos e iconos SVG genérico y maskable.

Políticas del Service Worker

RecursoPolíticaMotivo
Menú GETfreshness, timeout 3 s, máximo 30 días; menú IndexedDB emitido primero.Contenido consultable sin conexión y actualizado al recuperar red.
Lectura de pedidos GETfreshness, timeout 3 s, retención máxima 5 minutos.Prioriza estado actual y limita el respaldo potencialmente obsoleto.
Crear pedido POSTIndexedDB + reintento explícito con UUID.NGSW no encola POST. La confirmación debe venir del servidor.
Precisión técnica: Angular NGSW configura performance o freshness, no una política nativa llamada stale-while-revalidate. FastOrder produce el comportamiento SWR del menú en CatalogoService con IndexedDB y revalidación HTTP.

Sincronización de pedidos

El frontend guarda primero cada pedido en una transacción local; si está online, intenta sincronizarlo inmediatamente. Al reconectar, el evento de red dispara otro intento. Si el navegador cierra la pestaña, el pedido permanece local y se reintenta al abrir la PWA; este proyecto no promete ejecución de background sync con la app cerrada.

El servidor debe hacer la clave idempotente efectiva y recalcular precios/disponibilidad. La cabecera impide duplicados solo si la API persiste y aplica la clave de forma atómica.

POST /api/orders
Idempotency-Key: UUID

Notificaciones push: configuración y simulación

  1. Crear claves VAPID en el backend. Publicar solo la clave pública en la etiqueta meta vapid-public-key; la privada permanece como secreto del servidor.
  2. Desplegar sobre HTTPS y usar un build de producción para activar Angular Service Worker.
  3. Solicitar permiso desde la interacción del usuario; SwPush.requestSubscription registra la suscripción en POST /api/push/subscribe.
  4. Cuando cambie el pedido, enviar un Web Push firmado con título/cuerpo y data.orderId y data.status.
  5. Probar el mismo payload desde el backend de desarrollo; comprobar notificación, mensaje y paso del rastreador. Una notificación local del navegador no prueba transporte push.
{
  "notification": { "title": "FastOrder", "body": "Tu pedido está en preparación." },
  "data": { "orderId": "orden-servidor-123", "status": "preparacion" }
}

Respuestas a preguntas guía

¿Qué ventajas aporta una PWA frente a una app nativa?

Una PWA puede instalarse desde el navegador, compartirse mediante URL y actualizarse desde la web, reduciendo la fricción de distribución y permitiendo reutilizar tecnologías entre plataformas. Service Worker y almacenamiento local habilitan una experiencia tolerante a interrupciones de red. No todas las APIs, permisos ni políticas de instalación están disponibles por igual en cada navegador; una app nativa puede ofrecer integración más amplia y consistente con el sistema operativo.

¿Por qué se seleccionan estrategias de caché diferentes?

El menú permite mostrar contenido guardado y revalidarlo, mientras el estado de un pedido prioriza la respuesta de red por su naturaleza cambiante. El envío POST no se simula mediante caché: se guarda como operación pendiente hasta obtener confirmación. La fuente de verdad de precio, stock y estado siempre debe ser el backend.

¿Cómo se realiza el diseño responsivo?

Se parte de pantallas estrechas, controles táctiles y una jerarquía de lectura corta. CSS Grid adapta las tarjetas, Flexbox organiza encabezados y el carrito lateral se convierte en panel a pantalla completa en móviles. Las categorías son desplazables, el buscador filtra en el momento y los estados se acompañan con etiquetas, color y texto. Debe validarse con teclado, lectores de pantalla, zoom y dispositivos físicos.

¿Cómo se administra el modo offline?

El Service Worker conserva el app shell y las peticiones GET definidas; IndexedDB persiste menú, carrito y pedidos pendientes. La aplicación reintenta al reconectar o al iniciar. Una clave estable permite al backend deduplicar el reenvío. El usuario ve claramente “pendiente” hasta que el servidor confirma. El evento online no equivale a Background Sync: requiere que la aplicación vuelva a estar activa.

Validación y ejecución

Ejecutar npm test -- --watch=false --browsers=ChromeHeadless y npm run build. Para revisar offline, servir dist/villa001/browser en localhost o HTTPS, abrir online una vez, revisar el worker y Cache Storage, activar modo offline y recargar. Comprobar también que un pedido no figure como recibido antes de una respuesta válida del backend.

El código principal está organizado en src/app/app.component.* para la experiencia, storage.service.ts para IndexedDB, catalogo.service.ts para menú/SWR, order-sync.service.ts para la API, push.service.ts para Web Push y ngsw-config.json para caché.
