Runtime Caching con Angular 19

Implementación académica para consultar un catálogo con cobertura irregular y tratar precios y stock como información que necesita mayor frescura.

Proyecto: villa001 Angular: 19.2.25 Fecha: 2 de octubre de 2026

Resumen ejecutivo

El proyecto se convirtió de una plantilla inicial de Angular en una PWA académica operativa: muestra un catálogo ficticio, consulta precios/stock por separado y usa el Service Worker de Angular para conservar respuestas GET previamente utilizadas.

Alcance académico: nombres, precios, existencias y escenario son ficticios. No representan sistemas, productos, precios ni datos comerciales internos de Backus.

Políticas de caché y motivo

RecursoEstrategia AngularLímitesDecisión
/data/catalogo.jsonperformance20 respuestas · 1 díaPrioriza una respuesta ya conocida para que el catálogo siga disponible con señal irregular.
/data/precios.jsonfreshnessTimeout 3 s · 20 respuestas · 1 horaIntenta obtener precios y stock actuales; si falla o tarda, puede recurrir a la respuesta guardada.
Imágenes localesperformance60 recursos · 30 díasPrioriza carga rápida para contenido de cambio poco frecuente.
Fuentes localesperformance60 recursos · 30 díasReutiliza tipografías ya visitadas y limita el almacenamiento.
HTML, JS y CSS del app shellasset group / prefetchVersionado por buildSe descarga al instalar/actualizar el worker; no es un dataGroup runtime.
Lectura de Angular: en ngsw-config.json se escriben los valores performance y freshness. Conceptualmente corresponden a priorizar caché y priorizar red; no se escriben literalmente Cache First o Network First.

Prueba de disponibilidad offline

1 · Servir producciónEl Service Worker está deshabilitado durante ng serve.
2 · Calentar cachéVisitar catálogo y precios con conexión y confirmar ambas URLs en Cache Storage.
3 · Cortar redActivar Offline en DevTools y recargar; el catálogo previamente usado debe aparecer.

Cómo ejecutar y presentar

Desarrollo de interfaz

npm start
# http://localhost:4200/

Para que otro dispositivo vea el servidor de desarrollo en la red local:

npm run start:host
Importante: start:host sirve HTTP para desarrollo. Los Service Workers solo funcionan en contextos seguros: HTTPS o localhost. En un teléfono conectado a la IP LAN, usa un túnel HTTPS o un despliegue HTTPS para probar la PWA instalada.

Build y validación offline

npm run build
npx http-server ./dist/villa001/browser -p 8080
# abre http://localhost:8080/

Primero consulta los datos con conexión; después, en DevTools, confirma el worker en Application → Service Workers, las respuestas en Cache Storage y activa Network → Offline antes de recargar.

Alcance y límites

La solución cachea respuestas GET del catálogo y precios; no existe API de negocio conectada. El endpoint de precios es un JSON local de demostración, así que sirve para demostrar la política freshness, no para certificar precios reales.

Una solicitud POST para registrar un pedido no se guarda automáticamente con estos dataGroups. Pedidos offline exigirían IndexedDB, estados pendientes y una estrategia explícita de sincronización al volver la conexión.

La regla de imágenes y fuentes está lista para recursos que se agreguen bajo public/assets/images/ y public/assets/fonts/; el ejemplo actual no incluye fotografías de producto de marca.
